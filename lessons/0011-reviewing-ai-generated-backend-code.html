Bài 0011 — Review code AI tạo như senior backend engineer

Mission: dùng AI để tăng tốc nhưng vẫn chịu trách nhiệm về correctness.

Previous · Course map · Review checklist

AI output là hypothesis, không phải evidence

Code có thể compile, test unit pass, trông clean — nhưng vẫn oversell, leak data, break pagination hoặc mất Kafka event. Senior review bắt đầu từ behavior cần bảo vệ, không bắt đầu từ naming/style.

Luồng review 7 câu hỏi

  1. Contract: caller thấy status/body/header nào? Có phá OpenAPI/client cũ không?
  2. Invariant: điều gì không được sai? Ví dụ Available Quantity không âm, một key không tạo hai Order.
  3. Transaction boundary: write nào commit/rollback cùng nhau? Có network call khi giữ DB lock không?
  4. Side effect: event/log/retry xảy ra trước hay sau DB commit? Duplicate xử lý sao?
  5. Concurrency: hai request/replica chạy cùng lúc thì sao? Có đọc-then-ghi không atomic không?
  6. Persistence: migration, constraint, index, pagination có evidence không?
  7. Test evidence: integration test quan sát outcome thật hay chỉ mock private call?

Áp dụng vào atomic decrement

Giả sử AI đề xuất if (inventory.getAvailableQuantity() >= q) { inventory.set...; save(); }. Review không hỏi “code Java có đẹp không?”. Hỏi: hai request cùng đọc quantity = 1 thì sao? Evidence nào chạy PostgreSQL thật? Project chọn conditional update, ghi trong ADR 0002, và test concurrent HTTP để chứng minh accepted count/final inventory.

Áp dụng vào outbox

Nếu AI gọi kafkaTemplate.send() trong Order transaction, hỏi failure ordering: Kafka accepted rồi Order rollback thì consumer thấy gì? Nếu commit Order rồi mới send, Kafka down thì gì mất? Outbox là response có evidence cho hai câu hỏi này, không phải pattern dùng vì “senior code phải có Kafka”.

Câu trả lời phỏng vấn mẫu

“Bạn review AI-generated code thế nào?” — “Tôi xem AI output là hypothesis. Tôi trace từ public contract đến invariant, transaction and side-effect order, rồi thiết kế evidence tại boundary thật như HTTP + PostgreSQL/Testcontainers. Tôi review concurrency với nhiều request/replica và kiểm tra migration/observability. Tôi chỉ approve khi behavior, failure mode và test evidence khớp spec/ADR; style là bước sau.”

Capstone practice

Chọn PlaceOrder. Viết review 6 dòng, mỗi dòng trả lời: contract, invariant, transaction boundary, one failure mode, one concurrency risk đã chặn, và test evidence. Gửi lại cho mình; đó sẽ là evidence để tạo learning record đầu tiên.

Bạn đã có đủ lộ trình MVP. Hãy quay lại lesson bất kỳ khi cần, chạy practice, rồi dùng câu trả lời như câu trả lời phỏng vấn. Primary source: Patterns of Enterprise Application Architecture.

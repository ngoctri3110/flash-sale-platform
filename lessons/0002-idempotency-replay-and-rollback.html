Bài 0002 — Idempotency, replay và transaction rollback

Mission: retry an toàn khi client timeout mà không trừ stock hai lần.

Previous · Course map · Glossary

Tangible win

Bạn phân biệt được retry hợp lệ, reuse key sai payload, và rollback sau lỗi persistence.

Same customer/keyKết quảSide effect
Same product + quantity201 rồi 200Một Order, một deduction, một event
Different product/quantity201 rồi 409Lần hai không có side effect

Hai hàng rào

pg_advisory_xact_lock(customer:key) tuần tự hoá duplicate request đồng thời. Unique constraint (customer_id, idempotency_key) bảo vệ integrity ở database nếu code path khác sai. Đọc PlaceOrder và V3 orders schema.

Giải thích dễ hiểu

Idempotency nghĩa là “làm lại cùng một yêu cầu cho ra cùng một kết quả business, không sinh thêm tác dụng phụ”. Nó không có nghĩa “chặn request trùng”. Client có thể timeout sau khi server commit; retry là hành vi đúng và server phải trả Order cũ.

Advisory lock là lock logic do app đặt tên bằng customerId:key, không phải lock một table row. Nó xử lý race: request B cùng key phải chờ request A commit/rollback rồi mới lookup Order. Unique constraint là luật bền vững trong DB: ngay cả khi có bug/bypass lock, DB vẫn từ chối hai record cùng customer/key.

Rollback là hoàn tác các write trong transaction khi runtime exception thoát khỏi service. Trong test, trigger làm INSERT orders fail sau atomic decrement. Vì cùng connection/transaction, PostgreSQL rollback decrement; đó là evidence, không phải niềm tin vào annotation.

Senior trade-off: payload comparison hiện chỉ gồm productId và quantity. Khi request có voucher, address hay options, cần canonical request fingerprint/versioning; nếu không “same key” có thể trả nhầm kết quả cũ.

Câu trả lời phỏng vấn mẫu

“Unique key có đủ cho idempotency không?” — “Nó bảo vệ integrity nhưng không tự định nghĩa replay semantics hay giải quyết race thân thiện. Tôi dùng unique key làm hàng rào cuối; application lock cùng transaction làm duplicate concurrent request chờ rồi trả Order cũ. Tôi cũng so sánh payload để cùng key nhưng business input khác trả conflict thay vì im lặng replay.”

Practice

Trong OrderApiIntegrationTest, giải thích bốn test: identical replay, different-payload conflict, concurrent duplicate, và rollback khi trigger chặn insert.

Self-check

Kafka không được publish trước commit vì consumer có thể thấy event của Order cuối cùng rollback. Outbox record là database side effect nên rollback cùng Order.

Phản biện senior

  1. Key nên expire khi nào, và retention ảnh hưởng storage thế nào?
  2. Vì sao HTTP 200 hợp lý hơn 201 cho replay?
  3. Nếu cùng payload nhưng client đổi idempotency key, business có còn an toàn không?

Vấn đề thực tế

Nếu mỗi controller tự trả JSON kiểu {"message":"Sai rồi"}, frontend phải đoán text, test khó ổn định và support không biết log nào cần tìm. API contract tốt xem lỗi là response có cấu trúc, không phải exception leak ra ngoài.

Ba tầng validation

TầngVí dụLý do
Request shapequantity không null, từ 1 đến 5Chặn JSON sai trước business flow
Business validationProduct active, stock đủCần đọc state hiện tại từ DB
Database constraintstock không âm, unique idempotency keyHàng rào cuối khi app code có bug/race

Bean Validation là annotation như @NotNull, @Min, @Max trên CreateOrderRequest. Nó không thay thế business validation: annotation không biết stock hiện tại là bao nhiêu.

Problem Details là gì?

RFC 9457 Problem Details chuẩn hoá response lỗi HTTP: type (loại lỗi có URI), title (tóm tắt), status, detail, instance (request path). Project thêm extension ổn định: code cho frontend switch logic, fieldErrors cho form, traceId cho support.

{
  "type": "https://flash-sale.local/problems/validation-failed",
  "title": "Validation failed",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "fieldErrors": [{"field":"quantity","message":"must be greater than or equal to 1"}],
  "traceId": "..."
}

Đọc code theo luồng

ApiExceptionHandler là @RestControllerAdvice: một điểm tập trung chuyển exception thành public contract. RequestTraceFilter tạo UUID cho mỗi request, trả header X-Trace-Id và đặt nó vào log MDC. Với 500, server log stack trace cùng traceId nhưng client chỉ nhận safe detail — không lộ SQL hay internal class.

Câu trả lời phỏng vấn mẫu

“400, 404, 409, 500 khác gì?” — “400 là request shape không hợp lệ; client sửa input. 404 là resource không tồn tại. 409 là request hợp lệ về shape nhưng xung đột state/business hiện tại, như insufficient stock hoặc reuse idempotency key sai payload. 500 là server failure bất ngờ; tôi không trả stack trace mà trả traceId để tra log.”

Practice

Đọc tests public contract trong ProductApiIntegrationTest. Hãy tự thiết kế response cho: quantity = 0, productId không tồn tại, và stock không đủ. Mỗi response cần status, code, fieldErrors có/không, client action.

Gợi ý

400/VALIDATION_FAILED/có fieldErrors; 404/PRODUCT_NOT_FOUND/không fieldErrors; 409/INSUFFICIENT_STOCK/không fieldErrors. Đừng dùng 500 cho lỗi client có thể dự đoán.

Tiếp theo: PostgreSQL schema, Flyway migration, index và pagination. Hãy gửi ba response practice; mình sẽ review như API interviewer. Primary source: RFC 9457.

Bài 0006 — PostgreSQL schema, Flyway, index và pagination

Mission: biến business rule thành database evidence và giữ list API ổn định khi data lớn.

Previous · Course map · Quick reference

Schema không chỉ là table

Schema là nơi database tự bảo vệ sự thật business: available_quantity >= 0, foreign key Order → Product, unique customer/idempotency key. App validation cho error dễ hiểu; constraint là hàng rào cuối khi có race, script tay hoặc bug ở code path khác.

Flyway migration là lịch sử có thể lặp lại

Flyway chạy migration versioned theo thứ tự, ghi checksum vào schema history. Khi V3__create_orders.sql đã chạy ở shared environment, không sửa file đó: checksum mismatch và môi trường không còn tái tạo được. Thay đổi schema bằng migration mới, ví dụ project thêm V7__add_inventory_version_for_concurrency_lab.sql.

Index: trả lời “vì sao?” trước “tạo gì?”

Index giống mục lục sách: đọc nhanh hơn nhưng mỗi INSERT/UPDATE phải cập nhật thêm và tốn disk. Nó chỉ đáng có khi phục vụ query thật. Orders theo Product và newest-first dùng (product_id, created_at DESC, id DESC): cột filter trước, rồi cột order. Customer browse có index tương tự. Outbox dùng partial index chỉ chứa row chưa publish, vì worker không quan tâm event đã publish.

Senior habit: không nói “có index nên nhanh”. Dùng EXPLAIN (ANALYZE, BUFFERS), nhìn row estimate vs actual, scan type, sort, buffer reads; đo trên data shape gần production.

Offset pagination

LIMIT size OFFSET page*size dễ dùng cho admin MVP. Nhưng page càng sâu DB càng phải bỏ qua nhiều row. Project cap size 100 để một request không lấy vô hạn. Stable ordering nghĩa là luôn có tie-breaker unique: sort created_at DESC, id DESC. Nếu chỉ sort created_at, hai row cùng timestamp có thể đổi vị trí giữa page 1/page 2, gây duplicate hoặc missing item.

Khi cần scroll rất sâu hoặc table ghi liên tục, cân nhắc keyset pagination: truyền last seen (created_at,id) thay OFFSET. Trade-off: không jump trực tiếp tới page 500 và API contract phức tạp hơn.

Code cần đọc

Orders migration · Outbox partial index · Order query · bounded list parameters.

Câu trả lời phỏng vấn mẫu

“Bạn thiết kế index cho list endpoint thế nào?” — “Tôi bắt đầu từ actual WHERE, ORDER BY và cardinality, không index mọi column. Với Orders filter product và sort newest-first, composite index là product_id, created_at DESC, id DESC. Tôi thêm id vì stable pagination. Tôi xác nhận bằng EXPLAIN ANALYZE và cân nhắc write overhead. Với deep scroll, tôi cân nhắc keyset thay offset.”

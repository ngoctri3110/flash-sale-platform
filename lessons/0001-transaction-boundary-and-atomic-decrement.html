Bài 0001 — Transaction boundary và atomic decrement

Mission: chứng minh concurrent purchase không oversell bằng code và test thật.

Course map · Glossary · Practice

Tangible win

Bạn có thể giải thích tại sao Order, inventory decrement và outbox phải commit hoặc rollback cùng nhau.

Flow: validate → idempotency → read active Product → atomic decrement → insert Order → append outbox → commit. Một runtime exception ở bất kỳ bước nào rollback các database write trước đó.

Critical statement

UPDATE inventories SET available_quantity = available_quantity - :quantity
WHERE product_id = :productId AND available_quantity >= :quantity

Check và decrement là một statement ở PostgreSQL, nên không có lost update giữa hai request. Đọc PlaceOrder và JDBC store.

Giải thích từ mid đến senior

Transaction (giao dịch) là “gói thay đổi”: hoặc tất cả thay đổi database có hiệu lực, hoặc không thay đổi nào có hiệu lực. Trong project, gói đó là: trừ tồn kho, ghi Order, ghi outbox. Transaction boundary (ranh giới transaction) là nơi gói bắt đầu/kết thúc: method PlaceOrder.place().

Sai lầm mid-level phổ biến là viết: đọc stock = 1 → if (stock > 0) → update stock = 0. Hai request có thể cùng đọc 1 trước khi request nào update. Hai Order được accept: đó là lost update (một cập nhật bị che mất) và business thấy oversell.

Atomic update chuyển điều kiện business vào chính câu write. PostgreSQL sẽ re-check predicate khi row lock được lấy; request thứ hai không còn đủ stock sẽ update 0 row. Đây là điều quan trọng hơn annotation: @Transactional tạo commit/rollback, nhưng không tự biến read-then-write thành atomic.

Khi nào không đủ? Nếu quyết định phải kiểm tra nhiều row hoặc rule phức tạp, một câu atomic SQL có thể khó đọc. Khi đó cân nhắc pessimistic locking, optimistic versioning, hoặc redesign aggregate — nhưng luôn nêu invariant và contention cost trước khi chọn.

Câu trả lời phỏng vấn mẫu

“Làm sao chống oversell?” — “Tôi không dựa vào kiểm tra stock trong application. Tôi dùng conditional update ở PostgreSQL với predicate stock đủ. Affected row count là kết quả cạnh tranh: 1 là accept, 0 là insufficient stock. Tôi đặt decrement, Order và outbox trong một transaction để failure sau decrement rollback tồn kho. Tôi chứng minh bằng PostgreSQL integration test chạy 100 request đồng thời.”

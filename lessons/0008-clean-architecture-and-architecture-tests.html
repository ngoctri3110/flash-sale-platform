Bài 0008 — Clean Architecture nhẹ và architecture tests

Mission: thay đổi HTTP, database hoặc Kafka mà không làm business rule thành spaghetti.

Previous · Course map · Quick reference

Không phải “nhiều folder”

Clean Architecture là dependency direction: business/use case không phụ thuộc framework hay delivery detail. Nó không bắt bạn tạo 20 module và một interface cho mỗi class. Project dùng modular monolith theo feature: Order, Product, Inventory, Messaging; bên trong có API, application và infrastructure khi boundary có ý nghĩa.

Ví dụ Order

PlaceOrder diễn đạt use case: idempotency, product active, decrement, insert Order, append outbox. Nó phụ thuộc OrderPlacementStore — một port (hợp đồng application cần), không biết JDBC query cụ thể. Adapter JDBC ở infrastructure thực hiện port đó.

Lợi ích không chỉ là “dễ mock”. Use case được đọc như business narrative; thay PostgreSQL/JPA hoặc thêm test adapter không ép controller biết SQL. Nhưng nếu interface chỉ có một implementation và không có boundary thật, nó thêm ceremony mà không thêm giá trị.

Architecture tests

ArchitectureRulesTest dùng ArchUnit để cấm: application depend API/infrastructure; API reach vào infrastructure; domain depend Spring/JPA. Đây là test kiến trúc, không thay test behavior. Nó ngăn một shortcut nhỏ hôm nay thành coupling lớn ngày mai.

Senior trade-off: framework annotation trong application như @Service, @Transactional là pragmatic compromise của “clean architecture nhẹ”. Nếu yêu cầu portability cực cao mới tách transaction boundary ra adapter. Quan trọng là biết và ghi nhận trade-off.

Câu trả lời phỏng vấn mẫu

“Bạn áp dụng Clean Architecture thế nào?” — “Tôi không áp dụng máy móc. Tôi đặt use case và business contract ở application; persistence/messaging là adapter ngoài. Tôi tạo port khi có boundary đổi độc lập hoặc testable seam. Tôi giữ controller mỏng và không cho API depend JDBC implementation. Tôi dùng architecture tests để dependency rule không chỉ nằm trên sơ đồ.”

Practice

  1. Vì sao controller gọi thẳng JdbcClient làm test/unit architecture xấu đi?
  2. Khi nào interface là over-engineering?
  3. @Transactional trong application có phá Clean Architecture tuyệt đối không, và trade-off là gì?

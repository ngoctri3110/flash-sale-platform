Bài 0009 — Docker Compose, container hardening, metrics và trace ID

Mission: không chỉ chạy app; phải biết app healthy không và debug request lỗi thế nào.

Previous · Course map · Quick reference

Compose là local system contract

compose.yml định nghĩa backend, frontend, PostgreSQL và Kafka chạy cùng network. Container gọi nhau bằng service DNS như postgres:5432, kafka:9092; không dùng localhost vì localhost bên trong backend là chính backend container.

depends_on: service_healthy làm frontend đợi backend readiness và backend đợi Postgres. Nó làm demo lặp lại được, nhưng không thay retry logic production.

Image hardening cơ bản

Backend Dockerfile dùng multi-stage build: JDK stage compile jar, JRE stage chỉ chạy jar. Runtime image nhỏ hơn và ít build tool hơn. Nó tạo appuser rồi USER appuser; process không mặc định là root. Đây là baseline, không phải security tuyệt đối.

Health không phải một khái niệm

SignalCâu hỏiAction
LivenessProcess có bị kẹt/chết?Restart
ReadinessCó nhận traffic an toàn?Đưa vào/ra load balancer
MetricsHệ thống thay đổi thế nào?Dashboard/alert/investigate

Actuator expose health, readiness và metrics. Đừng dùng liveness để kiểm tra mọi remote dependency; Kafka tạm lỗi không nên restart Order API vẫn phục vụ DB request hợp lệ.

Trace ID: lần theo một request

RequestTraceFilter tạo UUID, trả header X-Trace-Id và đặt nó vào MDC log. User báo lỗi thì support lấy trace ID từ response để filter log; không cần đoán theo timestamp.

Smoke test

smoke-local.ps1 không thay integration suite. Nó kiểm tra packaged Compose stack: products có seed, tạo Order được, inventory giảm đúng một. Đây là critical path còn sống không sau startup.

Câu trả lời phỏng vấn mẫu

“Bạn quan sát và debug request thế nào?” — “Tôi tách readiness/liveness, expose metrics có chủ đích, và gắn trace ID xuyên response/log. Container chạy non-root multi-stage image và có smoke flow sau deploy. Trace ID liên kết client report với structured log; tôi không dựa vào log text tìm mơ hồ.”

Chương 1 · Bài 0001

Transaction boundary và atomic inventory

Nỗi đau: hai request cùng thấy stock = 1 và cùng tạo order. Stock cuối có thể không âm nhưng doanh nghiệp đã bán hai món.

Transaction là một nhóm thay đổi database cùng thành công hoặc cùng thất bại. Trong project, nhóm đó là: giảm Inventory, tạo Order và tạo Outbox event. Atomic update đặt điều kiện “còn đủ hàng” ngay trong câu lệnh ghi.

UPDATE inventories
SET available_quantity = available_quantity - :quantity
WHERE product_id = :productId
  AND available_quantity >= :quantity;

Database trả affected rows. `1` nghĩa là request đã reserve; `0` nghĩa là không đủ hàng. `@Transactional` bảo vệ rollback/commit, nhưng không biến đoạn `SELECT → if → UPDATE` thành atomic.

  1. Đọc PlaceOrder; khoanh vùng method có @Transactional.
  2. Đọc JdbcOrderPlacementStore; tìm câu update và giá trị boolean từ row count.
  3. Chạy Lab 01; ở phần sai tạo 2 accepted orders với stock ban đầu 1.
  4. Reset lab, chạy phần atomic; B phải nhận UPDATE 0 và không được insert order.
  5. Chạy integration test concurrency; kiểm tra initial = accepted + final.
Tự làm lại: viết một method `reserve(productId, quantity)` bằng JDBC trong scratch package. Viết test cho stock 1 với hai task đồng thời. Sau đó đổi thành read-then-write để test đỏ.
Phỏng vấn: “Tôi bảo vệ invariant bằng conditional update ở PostgreSQL; affected row 1/0 là kết quả cạnh tranh. Decrement, Order và outbox cùng transaction để lỗi sau decrement rollback. Tôi chứng minh bằng PostgreSQL concurrency test, không dựa vào `synchronized` trong một JVM.”

Chương 2 · Bài 0002

Idempotency, replay và rollback

Nỗi đau: client timeout sau khi server commit. User retry là hành vi bình thường; nếu retry tạo order thứ hai thì hệ thống tính tiền hoặc trừ stock hai lần.

Idempotency nghĩa là cùng actor + cùng key + cùng payload sẽ trả cùng kết quả business mà không lặp side effect. Project dùng advisory transaction lock để serialize cùng key và unique constraint để bảo vệ database.

Tình huốngHTTPSide effect
Lần đầu hợp lệ201Tạo một Order/stock decrement/outbox
Cùng key, cùng payload200 replayKhông tạo thêm
Cùng key, payload khác409Không tạo thêm
  1. Đọc header Idempotency-Key tại OrderController.
  2. Trong PlaceOrder, xác định thứ tự lock → lookup → compare payload → side effect.
  3. Chạy Lab 02 trên GitHub bằng hai terminal.
  4. Đọc test replay, different payload và rollback trong OrderApiIntegrationTest.
Tự làm lại: thêm một field vào command, tạo fingerprint payload và test cùng key nhưng khác fingerprint trả conflict. Ghi retention/expiry policy của key.
Phỏng vấn: “Unique constraint bảo vệ integrity nhưng không đủ cho replay semantics. Tôi lock cùng logical key trong transaction, trả order gốc nếu payload giống, conflict nếu khác. Idempotency không thay authentication.”

Chương 3 · Bài 0003

Atomic, pessimistic và optimistic locking

Nỗi đau: chọn `@Version` theo thói quen rồi tạo retry storm cho một SKU nóng, hoặc giữ `FOR UPDATE` trong lúc gọi mạng làm cả hàng đợi bị block.
StrategyCơ chếKhi dùng
AtomicMột conditional UPDATE, row count là outcomeMột row, rule đơn giản, hot path
PessimisticĐọc sau FOR UPDATE, request khác chờNhiều rule trong transaction ngắn
OptimisticVersion compare-and-set, conflict thì retryConflict hiếm, retry rẻ
  1. Đặt invariant: initial = accepted + final, stock không âm.
  2. Chạy strategy lab với stock 8, 24 attempts.
  3. Ghi accepted, rejected, p95, retries và lock-wait samples; đừng so sánh chỉ bằng average.
  4. Đổi workload thành một SKU cực nóng; dự đoán optimistic retry tăng thế nào.
Cố ý tạo lỗi: thêm sleep trong pessimistic transaction và quan sát lock wait; bỏ điều kiện version trong optimistic update và viết test chứng minh lost update.
Phỏng vấn: “Tôi chọn theo invariant và contention. Atomic là default cho decrement một row; pessimistic cho quyết định nhiều bước ngắn; optimistic cho conflict hiếm. Virtual thread không làm hot-row lock biến mất.”

Chương 4 · Bài 0004

JPA N+1 và fetch plan

Nỗi đau: một page có 20 Order nhưng mapper chạm Product lazy từng dòng. Database nhận 1 + N query; page lớn dần thì latency tăng theo dữ liệu.

Với 4 Order: một query lấy list + tối đa bốn query Product = 5. Vòng lặp Java không phải query; lazy association access mới phát query.

  1. Chạy NPlusOneQueryLabIntegrationTest.
  2. Dự đoán statement count cho lazy loop, fetch join, EntityGraph, batch và projection.
  3. Đọc ProductJpaRepository; list API dùng DTO projection.
  4. Đặt query budget regression; không chữa bằng bật EAGER toàn cục.
Tự làm lại: tạo list projection chỉ gồm id/name/price, rồi viết test fail khi mapper chạm association ngoài fetch plan.
Phỏng vấn: “List API ưu tiên projection; detail graph nhỏ dùng fetch join/EntityGraph; batch là fallback. Tôi đo statement count và giữ regression budget, không bật EAGER global.”

Chương 5 · Bài 0005

Validation và Problem Details

Nỗi đau: frontend phải đoán message lỗi, support không nối được request với log, và lỗi business bị trả như 500.

Ba lớp có vai trò khác nhau: request shape (`@Min`, `@NotNull`), business state (Product active/stock đủ), database constraint (unique/check/foreign key). Problem Details chuẩn hóa type/title/status/detail; project thêm code/fieldErrors/traceId.

  1. Đọc ApiExceptionHandler.
  2. Gửi quantity 0, thiếu Idempotency-Key, product không tồn tại và stock không đủ.
  3. Ghi expected status/code/fieldErrors trước khi xem test.
  4. Thêm một validation field và test response JSON; không leak stack trace/SQL.
Phỏng vấn: “Tôi tách malformed request khỏi business conflict, dùng error code ổn định và trace ID. Validation làm client feedback tốt; constraint và transaction vẫn bảo vệ correctness.”

Chương 6 · Bài 0006

Schema, Flyway, index và pagination

Nỗi đau: sửa migration đã chạy làm checksum mismatch; thêm index theo cảm giác làm write chậm; page sâu bằng OFFSET timeout.
  1. Đọc V3/V4 migration và truy vấn trong JdbcOrderQuery.
  2. Chạy EXPLAIN lab trước/sau composite index.
  3. Giải thích vì sao equality filter đứng trước sort keys và vì sao id là tie-breaker.
  4. So sánh offset với keyset trên page sâu; ghi execution time/buffers.
Phỏng vấn: “Index phải phục vụ query shape WHERE + ORDER BY; tôi chứng minh bằng EXPLAIN ANALYZE và tính write overhead. Migration dùng expand-contract, không sửa version đã chạy.”

Chương 7 · Bài 0007

Transactional Outbox và Kafka

Nỗi đau: database commit nhưng Kafka down làm mất event, hoặc Kafka nhận event trước khi database rollback.
transaction: inventory + order + outbox → COMMIT
publisher: claim → send Kafka → mark published
consumer: deduplicate eventId → side effect → acknowledge
  1. Đọc claim/lease.
  2. Chạy publisher test và vẽ failure timeline.
  3. Đọc consumer và processed-events table; gửi duplicate event để thấy side effect chỉ một lần.
  4. Thiết kế retry/backoff/DLT cho transient và poison message.
Phỏng vấn: “Outbox giải quyết dual-write loss, không tạo exactly-once end-to-end. Transport at-least-once nên consumer phải idempotent; claim lease và DLT làm failure có thể vận hành.”
Capstone: không chuyển sang microservices cho đến khi bạn tự vẽ và giải thích được bảy flow trên. Sau đó làm Lab hai service, rồi mới thêm timeout/config/gateway/resilience từng failure một.

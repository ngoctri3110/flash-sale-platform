Chương 8 · Bài 0008

Clean Architecture và dependency direction

Nỗi đau: controller biết SQL, service biết HTTP, test phải khởi động cả container; một thay đổi database lan khắp codebase.

Use case là câu chuyện nghiệp vụ; adapter là cách nói chuyện với HTTP/JDBC/Kafka. PlaceOrder phụ thuộc port OrderPlacementStore, còn JDBC adapter thực hiện port.

  1. Vẽ mũi tên API → application → port ← infrastructure.
  2. Mở ArchitectureRulesTest; đọc rule bị cấm.
  3. Viết fake port cho một unit test không Spring context.
  4. Đổi một dependency thành concrete JDBC trong branch thử; ghi testability/coupling mất gì.

Phỏng vấn: “Tôi dùng boundary khi nó cô lập business rule và dependency thay đổi. Tôi không tạo interface chỉ để có nhiều folder; architecture test biến dependency rule thành executable evidence.”

Chương 9 · Bài 0009

Docker, health, metrics và trace

Nỗi đau: “API lỗi” nhưng không biết container chết, pod chưa ready, DB hết connection hay Kafka publish fail.

Request cần một correlation ID. Health cũng tách loại: readiness quyết định nhận traffic, liveness quyết định restart, metrics cho biết xu hướng. Docker Compose là local wiring, không phải resilience đầy đủ.

  1. Chạy Compose và gọi endpoint có X-Trace-Id.
  2. Đọc RequestTraceFilter; tìm trace trong log.
  3. Xem Actuator readiness và metric Hikari/HTTP.
  4. Dừng Postgres/Kafka, ghi symptom, metric và recovery; không restart mù.

Phỏng vấn: “Tôi trace từ request ID đến DB/outbox/consumer, phân biệt readiness với liveness, và dùng metric để xác định bottleneck. Health endpoint không thay incident evidence.”

Chương 10 · Bài 0010

Kubernetes rollout và scaling

Nỗi đau: deploy pod mới chưa boot nhưng đã nhận traffic; tăng replicas làm database hết connection; rollback code không rollback dữ liệu.
  1. Đọc backend manifest và đánh dấu startup/readiness/liveness.
  2. Apply Kind stack, xem rollout status và Service endpoints.
  3. Xóa một pod trong lúc smoke order; quan sát request retry/idempotency.
  4. Chạy concurrency smoke; kiểm tra accepted quantity + final stock theo invariant.
  5. Đổi image/app version và xem rolling update; ghi downtime/rollback behavior.

Requests/limits là capacity contract cho scheduler/container; HPA chỉ tăng pod, không làm hot DB row hay connection pool rộng hơn. Migration expand-contract có lifecycle riêng; rollback Deployment không xóa cột đã dùng.

Phỏng vấn: “Readiness bảo vệ traffic, startup cho JVM warm-up, liveness phát hiện process không tiến triển. Tôi đo DB pool và lock trước khi scale pod, vì replica nhiều có thể làm bottleneck database nặng hơn.”

Chương 11 · Bài 0011

Review code AI bằng evidence

Nỗi đau: code compile và unit test xanh nhưng vẫn oversell, mất event hoặc lộ dữ liệu.

Review theo thứ tự rủi ro: contract → invariant → transaction → side effect → concurrency → persistence → test evidence. Style/naming chỉ review sau khi behavior đúng.

  1. Chọn một diff ở PlaceOrder.
  2. Viết timeline hai request trước khi đọc implementation.
  3. Chỉ ra test boundary thật: HTTP + PostgreSQL/Kafka, không chỉ mock private method.
  4. Đề xuất comment có severity, failure mode và test cần thêm.

Phỏng vấn: “AI output là hypothesis. Tôi chỉ approve sau khi contract, invariant, failure mode và evidence test khớp spec/ADR; style không được che lỗi correctness.”

Chương 12 · Capstone

System design: nói như senior/Tech Lead

Nỗi đau: câu trả lời phỏng vấn kể tên Kafka, Redis, Kubernetes nhưng không giải thích nguồn sự thật, failure hay trade-off.

Dùng thứ tự: requirement → invariant → decision → data/request flow → failure handling → evidence → trade-off.

  1. Scope: modular monolith, một Product mỗi Order, payment/auth out of scope.
  2. Correctness: idempotency lock, conditional inventory update, Order/outbox cùng transaction.
  3. Messaging: at-least-once, idempotent consumer, retry/DLT.
  4. Performance: projection, query budget, index theo query shape, p95/lock metrics.
  5. Operations: trace ID, health probes, rollout, smoke và rollback plan.
  6. Growth: chỉ tách service khi ownership/scale/failure isolation biện minh chi phí.
Bài capstone: trả lời 5 câu trong bài 0012 trong 2–3 phút không nhìn code, sau đó gửi sơ đồ và evidence test.

Phỏng vấn: “Tôi bắt đầu bằng invariant và source of truth, chọn cơ chế nhỏ nhất chứng minh được, nêu failure window và đo bằng test/metric. Khi scale, tôi thay đổi boundary dựa trên evidence, không tách microservice vì khẩu hiệu.”

Definition of done: bạn có thể vẽ flow, chạy một failure, giải thích vì sao test bắt được lỗi, và trả lời trade-off mà không đọc slide. Nếu thiếu một trong bốn, quay lại lab tương ứng.

Bài 0007 — Transactional Outbox và Kafka delivery

Mission: Order đúng dù Kafka tạm lỗi, nhưng event intent không bị mất.

Previous · Course map · Quick reference

Vấn đề dual write

Order flow cần ghi PostgreSQL và gửi Kafka. Commit DB trước rồi Kafka down: Order có nhưng event mất. Send Kafka trước rồi DB rollback: consumer thấy event của Order không tồn tại. Đây là dual-write gap.

Outbox giải quyết thế nào?

Trong cùng transaction tạo Order, app insert row outbox_events: đây là ý định phải publish, không phải Kafka send. Commit thành công nghĩa là Order và intent luôn cùng tồn tại. Worker chạy sau commit đọc pending outbox rồi gửi Kafka.

INSERT orders
INSERT outbox_events  // durable publish intent

publisher: claim pending → Kafka send → mark published

Retry và nhiều replica

claimPending() dùng FOR UPDATE SKIP LOCKED: worker A claim row thì worker B bỏ qua. Lease expiry tránh row kẹt mãi khi publisher chết. Send fail thì tăng attempts và đặt next_attempt_at để retry.

At-least-once delivery nghĩa là event có thể đến nhiều hơn một lần. Nếu Kafka send thành công nhưng app crash trước mark-published, publisher gửi lại. Đây là expected failure mode, không phải lỗi có thể xoá chỉ bằng retry.

Consumer idempotency

Audit store insert event ID vào processed_events với ON CONFLICT DO NOTHING. Nếu trả 0, event đã xử lý và side effect audit không chạy lại. Đây là deduplication/inbox pattern.

Không claim exactly once: project có at-least-once transport với idempotent consumer. Exactly-once end-to-end phải xét mọi boundary và side effect ngoài DB.

Câu trả lời phỏng vấn mẫu

“Vì sao dùng outbox?” — “Để tránh dual-write gap. Tôi persist Order và outbox event trong cùng local transaction. Publisher retry pending rows; Kafka có thể duplicate nên consumer ghi processed event ID atomically trước side effect. Đây là at-least-once với idempotent consumer, không phải exactly-once end-to-end.”

Code và practice

Đọc claim/lease store, publisher, và consumer.

  1. Kafka down lúc Order create: DB nào commit và HTTP response là gì?
  2. Crash sau Kafka send nhưng trước markPublished tạo duplicate ra sao?
  3. Vì sao unique Kafka key không tự deduplicate consumer side effect?

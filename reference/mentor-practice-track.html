Không học bằng cách đọc hết repository. Mỗi sprint nhỏ: dự đoán → quan sát → tự làm lại → tạo failure → viết test → giải thích trade-off.

Definition of done cho từng bài

  1. Không nhìn code, vẽ được request/data flow trong 2 phút.
  2. Tự nói được invariant (điều luôn phải đúng) và failure mode.
  3. Tự code được phần nhỏ trong branch/lab, không copy đáp án.
  4. Có test đỏ khi phá invariant và test xanh sau khi sửa.
  5. Trả lời được: tại sao chọn cách này, không chọn cách khác, trade-off là gì.
Quy tắc mentor: bạn gửi diff hoặc mô tả reasoning trước. Mentor chỉ gợi ý theo tầng: câu hỏi → pseudo-code → đoạn code nhỏ. Chỉ xem đáp án project sau khi đã thử.

Track A — Order correctness: transaction, idempotency, concurrency

A1. Đi theo một request đặt hàng

Đọc theo thứ tự: OrderController → PlaceOrder → OrderPlacementStore → JdbcOrderPlacementStore.

Việc bạn làm: vẽ 7 bước: HTTP validation, lock idempotency key, replay check, product check, conditional decrement, insert order, append outbox/commit. Ghi data nào đọc/ghi tại mỗi bước.

Checkpoint: giải thích vì sao @Transactional đặt ở use case, không ở controller; và vì sao controller không gọi JDBC store trực tiếp.

Chạy: cd backend; .\mvnw.cmd -Dtest=OrderApiIntegrationTest test. Trước khi chạy, dự đoán các status 201/200/409.

A2. Tự viết atomic decrement

Invariant: available_quantity >= 0, và tổng quantity accepted không vượt stock ban đầu.

Bài code: trong một scratch branch hoặc test fixture, tự viết method trả boolean dùng đúng một SQL statement: UPDATE inventories ... WHERE product_id = ? AND available_quantity >= ?. Affected row count 1 là accepted, 0 là insufficient stock.

Cố ý làm sai: thay bằng “SELECT stock → if → UPDATE” và chạy concurrent test. Nêu timeline hai request cùng đọc stock = 1. Đó là race condition; vòng lặp Java không tự tạo transaction isolation.

Evidence: đọc và chạy InventoryConcurrencyStrategyLabIntegrationTest. Sau đó giải thích atomic SQL, pessimistic locking và optimistic locking: cơ chế, contention cost, retry behavior, khi nào chọn.

A3. Idempotency và rollback

Bài code: gửi cùng customer + Idempotency-Key hai lần; lần hai phải replay cùng order, không trừ tồn kho lần nữa. Cùng key nhưng payload khác phải là conflict. Quan sát pg_advisory_xact_lock và unique constraint migration V3.

Phỏng vấn: advisory lock serialize cùng key trong transaction; unique constraint là hàng rào cuối. Khác key không bị serialize. Đây không phải distributed lock cho toàn bộ inventory.

Track B — Java, OOP, SOLID và patterns

B1. Trách nhiệm và dependency direction

Đọc: port, adapter, ArchitectureRulesTest.

  • SRP: controller dịch HTTP; use case điều phối business flow; store truy cập persistence.
  • DIP: PlaceOrder phụ thuộc abstraction OrderPlacementStore, không phụ thuộc JDBC class.
  • Pattern có thật: Ports-and-Adapters/Repository boundary, Strategy qua interface; không thêm Factory/Builder chỉ để “có pattern”.

Bài code: thêm một fake/in-memory implementation chỉ cho unit test của PlaceOrder, không Spring context. Sau đó đổi constructor dependency thành JDBC concrete class và mô tả testability/architecture nào bị mất.

Cần tránh: interface một-method vô nghĩa, service god class, entity/DTO dùng chung mọi layer, pattern vì tên đẹp hơn vì giảm complexity.

B2. Java concurrency thật sự

Repo chứng minh concurrent requests qua test, nhưng chưa dạy hết Java thread primitives. Hãy học theo thứ tự: process vs thread → executor/thread pool → blocking I/O → race condition → visibility → synchronized/volatile/atomic classes → CompletableFuture → virtual threads Java 21.

Bài code độc lập: viết counter không synchronized, chạy 100 task trong ExecutorService, rồi sửa bằng AtomicInteger. Sau đó trả lời vì sao cách đó không thay atomic SQL khi có hai backend replica: memory mỗi JVM khác nhau, PostgreSQL mới là source of truth.

Senior checkpoint: không dùng virtual thread để “sửa” database contention; nó tăng concurrency khả dụng, không làm hot-row lock biến mất.

Track C — JPA, SQL và performance

C1. N+1 từ quan sát SQL

Đọc/chạy: NPlusOneQueryLabIntegrationTest. Dự đoán query count trước khi chạy: 1 query list Order + tối đa N query Product; loop Java không phải query, lazy association access mới kích hoạt query.

Bài code: thay list query bằng projection cho đúng response fields. So sánh DTO projection, fetch join, EntityGraph, batch fetching. Không đổi mọi association thành EAGER: EAGER chỉ chuyển hidden loading sang nơi khó đoán.

C2. Index và EXPLAIN ANALYZE

Đọc: migrations V3 orders indexes và V4 browse index; order query implementation. Trước khi đề xuất index, ghi query filter + sort + page shape.

Bài code/DB: seed nhiều orders, chạy EXPLAIN (ANALYZE, BUFFERS) cho browse query trước/sau index. Giải thích Seq Scan, Index Scan, rows estimate, sort, heap fetch. Chỉ giữ index phục vụ query thật; mỗi index làm INSERT/UPDATE tốn thêm write và disk.

Checkpoint: offset pagination dễ hiểu nhưng page sâu chậm/không ổn định khi data thay đổi. Tự thiết kế cursor keyset bằng (created_at, id).

Track D — reliability, Kafka, microservice boundary

D1. Outbox là gì và không là gì

Đọc/chạy: OutboxPublisherIntegrationTest, OrderEventConsumerIntegrationTest, migration V5.

Bài reasoning: Kafka down sau DB commit: Order vẫn đúng; outbox còn pending và publisher retry. Consumer nhận duplicate: dùng event ID/processed-events để side effect chỉ một lần. Đây là at-least-once delivery + idempotent consumer, không phải magical exactly-once end-to-end.

Bài code: thêm một consumer side effect giả lập, rồi test publish cùng event hai lần mà audit chỉ có một record. Sau đó thiết kế DLQ/retry backoff và nêu khi nào phải alert.

D2. Khi nào mới tách microservice

Repo hiện là modular monolith có event worker — lựa chọn phù hợp MVP. Chỉ tách service khi ownership, deployment cadence, scale hoặc data boundary tạo lợi ích lớn hơn distributed failure: network timeout, contract versioning, tracing, eventual consistency, operational cost.

Bài thiết kế: tách “notification” trước (read/event side effect, failure tách biệt), không tách Inventory/Order khi vẫn cần transaction mạnh cho một business invariant.

Track E — mở rộng sang booking và finance

E1. Hotel/flight booking

Bài domain: thêm Reservation state machine: PENDING → CONFIRMED | EXPIRED | CANCELLED. Khi PENDING, giữ inventory trong 10 phút; expiry worker phải idempotent. Tạo migration, command, transaction test và concurrent hold test.

Tại sao khó hơn flash sale: một booking có thể chạm nhiều inventory unit/segment, có pricing thay đổi và cancellation. Cần xác định aggregate/invariant trước khi chọn lock.

E2. Banking/finance: không dùng Order làm ledger

Nguyên tắc: tiền cần immutable double-entry journal. Một transfer tạo tối thiểu debit và credit cùng transaction; balance là projection/derived value có reconciliation. Không UPDATE “balance = balance - amount” rồi ghi một event là đủ cho audit.

Bài thiết kế trước khi code: vẽ Account, JournalEntry, JournalLine, Transfer. Invariant: tổng debit = tổng credit theo currency; journal đã posted không bị sửa/xóa; request replay không tạo bút toán lần hai. Viết database constraints, idempotency strategy, audit/reconciliation job, authorization boundary.

Điều bắt buộc bổ sung trước production: authentication/authorization, secret management, encryption/PII handling, audit access, fraud/risk controls, regulatory retention và incident/runbook. Đây là domain/compliance work, không chỉ là Spring annotation.

Track F — vận hành và phỏng vấn

Đọc: các bài 0009–0012. Chạy local Compose/Kind smoke. Với mỗi lỗi “order created but audit missing”, nêu trace ID, outbox status, publisher log, Kafka consumer offset/processed-events row và metric cần xem theo đúng thứ tự.

Mock interview answer template: requirement → invariant → decision → transaction/data flow → failure handling → evidence test/metric → trade-off/alternative. Không bắt đầu bằng danh sách Kafka, Kubernetes, Redis.
